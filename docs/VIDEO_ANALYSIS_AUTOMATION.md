## 1. 현재 파이프라인 요약

```
파일 업로드(blob, ≤100MB)
  → seek 기반 샘플링 (20fps, 최대 280프레임 / 14초)
  → 프레임당 ImageBitmap 2개 생성
      ├─ pose.worker  : MediaPipe Pose Lite, numPoses=3
      └─ ball.worker  : 프레임 차분(motion diff) 블롭 검출, 420px 폭
  → 프레임별 휴리스틱
      · 발: landmark 31/32 중 "가장 빠른 발" 전역 선택 (>300 px/s)
      · 공: 크기/원형도/발 거리/이전 공 거리 랭킹으로 1개 선택
      · 임팩트: 공 속도 >220 px/s + 발 근접 확인
  → 속도: (공 시작→끝 픽셀거리) / (코–발목 픽셀 ÷ 키) / 경과초 × 3.6
  → 보정: ReferenceVideo 테이블의 global median factor (0.5~1.6 clamp)
  → 폼 점수: 무릎각 + 상체 기울기 (2D)
```

구조 자체(워커 분리, run-id 취소, 요청 ID 매칭, 레퍼런스 보정 테이블)는 잘 잡혀 있다.
문제는 **측정 원리**와 **검출기 품질**, 그리고 **검증 자동화 부재**에 집중돼 있다.

## 2. 정확도를 무너뜨리는 근본 원인 (우선순위 순)

### 2.1 타임스탬프가 실제 프레임 시각이 아님 ★★★
`waitForVideoSeek()`가 `video.fastSeek()`를 우선 사용한다. `fastSeek`은 **가장 가까운 키프레임으로 스냅**해도 되는 API다.
그런데 속도 계산에 쓰는 시각은 실제 표시 프레임이 아니라 `timestamp = targetTime * 1000`(요청값)이다.

- 25fps 방송 클립, 비행 구간 0.4~0.5초 → 유효 샘플 8~10개.
- dt가 1프레임(40ms)만 어긋나도 속도 오차 **±10% 이상**.
- 키프레임 스냅이 걸리면 여러 샘플이 같은 프레임을 가리켜 dt=0에 가까운 구간이 생긴다.

→ `requestVideoFrameCallback`의 `mediaTime`(실제 표시 프레임 시각)을 쓰거나, `fastSeek` 제거 + 정확 seek로 전환해야 한다. **가장 싸고 효과가 큰 수정.**

### 2.2 2D 투영 거리로 3D 속도를 추정 ★★★
`lib/analysis/speed.ts`는 공의 **화면상 이동거리**를 그대로 실제 이동거리로 간주한다.
프리킥/페널티킥은 대개 카메라 광축 방향(깊이 방향)으로 날아가므로, 투영 거리는 실제 거리보다 크게 작다.
→ 89km/h가 40~50km/h로 나오는 전형적 원인. **global scalar 보정으로는 절대 못 고친다** (오차가 깊이 변화에 따라 비선형).

해결 후보(권장 순):
1. **공 지름 기반 깊이 추정**: 실제 지름 0.22m + 프레임별 공 픽셀 지름 → 핀홀 모델로 프레임별 깊이 z 산출 → 3D 변위 계산. 검출 bbox 품질이 전제.
2. **골대/필드 호모그래피**: 골대(7.32×2.44m), 페널티 스팟(11m), 골 에어리어 라인 등 알려진 길이로 지면 평면 스케일 확보.
3. **최소한의 방어**: 깊이 방향 이동이 크다고 판단되면 속도를 숨기고 "측면 촬영 필요" 안내.

### 2.3 카메라 이동(에고모션) 미보정 ★★★
패닝/줌이 있으면 (a) 프레임 차분 검출기가 화면 전체를 움직임으로 인식하고, (b) 공 픽셀 변위에 카메라 움직임이 그대로 더해진다.
→ 배경 특징점/블록 매칭으로 전역 affine을 추정해 차감해야 한다. 모바일 손각대 촬영에서도 필수.

### 2.4 공 검출기가 학습 모델이 아님 ★★★
`ball.worker.ts`는 순수 프레임 차분 + 블롭 필터다. 외형 모델이 없어 골키퍼/키커/자막/그래픽/그림자를 공으로 잡는다.
게다가 해상도 손실이 심하다:

```
1080p → 분석 프레임 960px → 모션 분석 420px
11m 거리의 공 ≈ 원본 25px → 420px 공간에서 5~6px
(블롭 최소 조건: area≥4, maxSide≥4)
```

즉 임계값 바로 위에서 노이즈와 경쟁한다. **ROI 2단계 검출(coarse → 원본 해상도 크롭 재검출)** 이 없으면 어떤 튜닝도 한계.

### 2.5 속도를 2점(시작/끝)만으로 계산 ★★
`buildFinalResult()`는 `ballStartPos → ballEndPos` 한 쌍만 쓴다. 두 점 중 하나만 오검출이면 결과 전체가 망가진다.
→ 궤적 5점 이상에 **RANSAC 직선/포물선 피팅** 후 기울기로 속도 산출 + 잔차를 신뢰도로 사용.

### 2.6 신체 스케일 기준의 계통 편향 ★★
`bodyPixels = distance(nose, ankle)`를 **전신 키**로 나눈다. 코–발목 구간은 실제 키의 약 0.88배이므로 px/m를 약 12% **과소평가** → 거리·속도를 **약 14% 상시 과대평가**.

> 예: 키 1.75m, 코–발목 176px → 올바른 px/m = 176 / (1.75×0.88) = 114.3. 기존 코드는 176 / 1.75 = 100.6.
> 공이 500px 이동하면 실제 4.37m인데 기존 코드는 4.97m로 계산.

게다가 상체를 숙이거나 사선으로 서면 이 값이 더 줄어든다. 최소한 0.88 계수 보정, 근본적으로는 `worldLandmarks`(MediaPipe 3D 미터 좌표) 기반 스케일로 교체.

이 편향은 2.2(2D 투영에 의한 과소평가)와 **방향이 반대라 서로 일부 상쇄**되고 있었다. 0.88 보정만 적용하면 정면 촬영 클립은 오히려 더 낮은 값이 나온다.

### 2.7 임계값이 절대 픽셀 단위 ★★
`FOOT_VELOCITY_THRESHOLD 300px/s`, `BALL_VELOCITY_THRESHOLD 220px/s`가 해상도·줌·피사체 크기와 무관한 상수다.
→ **키커 신장 픽셀(또는 프레임 폭)로 정규화**해야 원거리/근거리 영상이 같은 기준으로 동작한다.

### 2.8 키커 추적이 프레임 단위 "가장 빠른 발" ★★
`numPoses=3`으로 늘렸지만 선택 로직은 여전히 프레임마다 독립적이고, 전환 페널티만 약하게 걸린다.
골키퍼가 다이빙하는 순간 대상이 바뀔 수 있다.
→ IoU/거리 기반 **person track ID 유지**, 공 근접·전신 노출·크기로 키커를 한 번 고정.

### 2.9 컷 편집 감지 없음 ★★
방송 클립의 인트로/리플레이/레이더 화면 전환에서 추적 상태가 그대로 이어진다.
→ 히스토그램 차이 급증으로 씬 컷 감지 → 트래커 리셋 + 구간 분리 분석. 구현 난이도 낮고 효과 큼.

### 2.10 폼 점수의 프레임 선택과 2D 각도 ★
`formResultRef`는 "발 속도 임계값을 넘긴 마지막 프레임"에서 갱신된다. 임팩트 프레임이 아니다.
또한 2D 각도라 촬영 각도에 따라 값이 흔들린다.
→ 임팩트 프레임 기준 ±1프레임으로 고정 + `worldLandmarks` 3D 각도 사용.

### 2.11 신뢰도 표기가 사실상 이진 ★★
`finalSpeed > 0`이면 `confidence: "high"`. 위 오차 요인들을 감안하면 **틀린 값에 high가 붙는다** — 신뢰 훼손이 가장 큰 항목.
→ dt 양자화 오차 + 스케일 불확실성 + 궤적 피팅 잔차를 전파해 `89 ± 12 km/h` 형태의 구간 제시. 불확실성이 크면 수치 대신 등급/재촬영 안내.

### 2.12 보정 계층이 오차를 덮고 있음 ★
`applyReferenceCalibration`의 0.5~1.6 clamp와 200km/h cap은 "그럴듯한 숫자"를 만들지만 원인을 가린다.
조건(촬영 각도/거리/fps/기기)별 calibration set 없이 global median 하나로는 구조적 오차를 보정할 수 없다.

## 3. 자동화 파이프라인 관점의 공백

### 3.1 검증 자동화가 없다 (가장 큰 공백)
레퍼런스 DB와 `Cut + Analyze` 워크플로우는 있지만, **회귀 측정 지표가 없다.**
알고리즘을 고쳐도 좋아졌는지 나빠졌는지 숫자로 말할 수 없다.

필요한 것:
- 고정 fixture 클립 세트(각 클립: 실제 속도, 촬영 각도, fps, 거리 태그)
- headless 실행기 — Playwright로 `/analyze` 자동 구동하거나, 분석 코어를 브라우저 DOM에서 분리해 Node + WebCodecs/ffmpeg에서 직접 실행
- 리포트: 전체/조건별 **MAE, bias, P90 오차, 실패율**
- CI에서 임계값 초과 시 실패 처리

→ **선행 조건: 분석 코어의 순수 함수화.** 현재 로직이 `app/analyze/page.tsx`(1,515줄)의 ref/useCallback에 묶여 있어 단위 테스트가 불가능하다.
`lib/analysis/pipeline/` 로 분리(입력: 프레임 시퀀스 + 메타, 출력: 궤적/임팩트/속도/신뢰도)하는 리팩터링이 사실상 모든 개선의 전제다.
`lib/analysis/client-video-analyzer.ts`가 이미 유사한 분리를 시작했으므로 **두 경로를 하나로 통합**하는 것이 맞다.
(현재 `/analyze`와 admin 분석기가 로직을 중복 보유 → 개선이 한쪽에만 반영될 위험.)

### 3.2 데이터 수집 루프가 끊겨 있다
`app/api/dataset/upload/route.ts`는 `process.cwd()/.data/uploads`에 파일을 쓴다.
**Vercel 서버리스에서는 동작하지 않는다**(읽기 전용/휘발성 FS). 즉 `docs/AI_TRAINING_GUIDE.md`가 전제한 학습 데이터 축적이 프로덕션에서 사실상 0이다.
→ Blob/S3 presigned URL 업로드로 교체 + 동의 상태/보존기간/삭제 경로 명시.

### 3.3 라벨링–학습–배포 경로가 수동
Roboflow → Colab → `public/model/` 수동 복사 구조. 모델 교체 시 회귀 측정이 없다.
→ 3.1의 eval 하니스가 생기면 "모델 후보 → 자동 평가 → 승격" 흐름으로 연결 가능.

### 3.4 입력 사전 점검(pre-flight)이 없다
실패 후 "다시 업로드하세요"만 나온다. 분석 전에 자동 판정 가능한 항목:
fps, 해상도, 길이, 화면 내 인물 크기 비율, 카메라 이동량, 씬 컷 수, 공 후보 안정성.
→ 분석 시작 전 5초 프리스캔으로 "이 영상은 정면 촬영이라 구속 정확도가 낮습니다" 같은 **행동 가능한 안내**를 준다. 실패율 자체를 줄이는 가장 저렴한 수단.

### 3.5 처리 성능
프레임당 `seek → ImageBitmap 2개 생성 → 워커 2개 응답 대기 → 다음`의 완전 직렬 구조.
280프레임이면 seek 왕복만으로도 수십 초. 파이프라이닝 없음, 프레임 재사용 없음.
→ WebCodecs `VideoDecoder`로 순차 디코딩하면 정확한 프레임 타임스탬프(2.1 해결)와 처리량을 동시에 얻는다. Safari 지원은 seek 폴백 유지.

## 6. 열린 질문 (결정 필요)

- **타깃 촬영 조건을 좁힐 것인가?** "측면 촬영, 공과 전신이 프레임의 X% 이상"으로 제한하면 2.2의 깊이 문제를 상당 부분 회피할 수 있다. 정확도 vs 사용 편의의 트레이드오프.
- **서버 정밀 분석 모드를 둘 것인가?** 영상 비저장 정책과 충돌. opt-in 임시 처리(분석 후 즉시 삭제)로 우회 가능한지 확인 필요.
- **레퍼런스 클립의 라이선스/보관 정책** — 방송 클립을 fixture로 커밋할 수 있는지.
